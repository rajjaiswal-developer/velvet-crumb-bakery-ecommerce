## Architecture Decisions

- **Database**: PostgreSQL + Prisma, replacing the original MongoDB
  plan — chosen for schema-enforced correctness (stock CHECK
  constraints, real multi-statement transactions), which matters
  more than usual here because the codebase is being built
  incrementally by an AI agent across many sessions.
- **Backend architecture**: no standalone Express server — all
  backend logic lives in Next.js API routes (Route Handlers),
  deployed serverless on Vercel's free Hobby tier. Avoids the
  cold-start/reliability problems of free tiers on Render/Railway
  without any recurring hosting cost.
- **Storefront Cart**: Server-side signed HttpOnly JWT cookie (`cart_session`) storing item references (`variantId`, `quantity`). Live price, stock availability, and item details are resolved against PostgreSQL on every cart API request to prevent price or stock tampering.
- **Rate Limiting**: Database-backed `LoginAttempt` model in PostgreSQL (`lib/auth/rate-limit.ts`), preventing rate limit bypass across isolated Vercel serverless function instances with opportunistic cleanup of expired records older than 15 minutes.
- **Session authentication**: `jose` library using HS256 JWTs stored in HttpOnly, SameSite=Strict cookies (`admin_session`), verified inside `middleware.ts` for fast serverless edge/Node route protection.
- **Image storage**: ImageKit over Cloudinary — integrated via `@imagekit/nodejs` server SDK.
- **Email**: Brevo over Resend — Resend's free tier caps at 100
  emails/day, which is below the client's 200-orders/day target.
  Brevo's free tier gives 300/day, forever, no card required.
- **Phone verification**: no automated SMS/WhatsApp OTP (avoids
  ongoing per-message cost). Verification layer is: double-entry
  phone field + format validation + pre-payment review screen +
  admin's manual confirmation call/WhatsApp before "Processing".
- **Inventory reservation**: stock is reserved (not just decremented)
  at checkout/Razorpay-order-creation time, with a 15-minute TTL,
  confirmed on payment success and released on failure/timeout —
  prevents both overselling and the worse case of a customer paying
  for an already-sold-out item.
- **Order/payment state machine**: `orderStatus` (Order Received →
  Processing → Packaging → Out for Delivery → Delivered) and
  `paymentStatus` (Pending → Success/Failed/Cancelled/Expired) are
  independent fields with enforced valid transitions.
- **Background jobs**: no Redis/BullMQ (over-engineered for ~200
  orders/day). Notifications use a Postgres `NotificationOutbox`
  table + Vercel `waitUntil()` for immediate non-blocking delivery,
  backed by a free GitHub Actions scheduled workflow (every 5-10
  min) for retries and expired-reservation cleanup — works around
  Vercel Hobby's cron limitation of once-per-day.
- **Geocoding**: Google Maps Geocoding API + Haversine formula in
  application code, not the Distance Matrix/Routes API — the
  business rule is a straight-line 5km radius, not drive-time/road
  distance, so the simpler/cheaper API is the correct fit, not a
  compromise.
- **Backups**: scheduled `pg_dump` via the same GitHub Actions
  workflow, pushed to Backblaze B2's free 10GB tier — Neon's free
  plan only offers 6h point-in-time recovery, not real backups.
- **Image sizing**: no pre-generated thumbnail/medium/large copies
  stored — ImageKit's on-the-fly transformation URLs handle
  responsive/optimized delivery, avoiding redundant storage and
  custom pipeline code.
- **Dependency Vulnerability Audit & Next.js Upgrade Deferral**: Ran safe non-breaking `npm audit fix` for `brace-expansion`. The Next.js 14 → 16 major version upgrade (and associated `postcss` / `glob` advisory updates) is deferred to a future dedicated maintenance cycle by deliberate decision. A real-exposure investigation confirmed all 3 remaining advisory groups carry Low real-world risk for this application: (1) `next/image` and the Image Optimizer are never used (ImageKit + plain `<img>` tags are used per Fix-16), and middleware is scoped strictly to `/admin/*`; (2) `postcss` runs only at build time; (3) `glob` is a transitive dev-tooling dependency via ESLint. Deferring avoids major-version regression risk close to launch without exposing the application to actionable real-world security vulnerabilities. To be revisited during routine maintenance or when new features require Next.js 15+.
